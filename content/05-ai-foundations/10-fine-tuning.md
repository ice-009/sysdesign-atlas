## First: should you fine-tune at all?

Most fine-tuning projects should have been prompt engineering or retrieval projects. The honest decision table:

| Problem | Right tool |
|---|---|
| Model lacks knowledge of your data | **Retrieval.** Fine-tuning teaches style, not facts, and teaches them unreliably |
| Output format is wrong | **Constrained decoding.** Guaranteed, immediate, free |
| Model doesn't follow instructions well | **Better prompt** first; fine-tune only if a large prompt is the problem |
| You need a specific voice, tone, or domain style | **Fine-tuning.** This is what it's genuinely good at |
| Task is narrow and high-volume | **Fine-tune a small model** — often 10-50× cheaper to serve than prompting a large one |
| Latency or cost is unacceptable | **Distil** a large model's behaviour into a small one |

:::goat The one that actually pays for itself
The strongest economic case for fine-tuning is **distillation into a smaller model for a narrow, high-volume task**.

Classifying support tickets with a frontier model via a 2,000-token prompt is expensive at a million tickets a day. Fine-tuning an 8B model on 50,000 labelled examples — generated by the frontier model — often matches its accuracy on that one task at a fraction of the cost and a tenth the latency.

The pattern: **use the big model to create the training data, then serve the small one.** That's a clear, measurable win. "Fine-tune so the model knows about our product" is usually neither.
:::

## Full fine-tuning: what it costs

Updating every parameter requires holding far more than the weights.

:::derive Memory for full fine-tuning
```
   7B parameter model, BF16, Adam optimizer:

     weights                    7B × 2 bytes  =  14 GB
     gradients                  7B × 2 bytes  =  14 GB
     Adam momentum (FP32)       7B × 4 bytes  =  28 GB
     Adam variance (FP32)       7B × 4 bytes  =  28 GB
     FP32 master weights        7B × 4 bytes  =  28 GB
                                                ───────
     subtotal                                   112 GB
     + activations (batch and sequence dependent)  ~10-40 GB
                                                ───────
     total                                     ≈ 120-150 GB

   → A 7B model needs 2 × 80 GB GPUs to fine-tune,
     while it INFERENCES comfortably on one at BF16.

   Training memory ≈ 16-20 bytes per parameter.
   Inference memory ≈ 2 bytes per parameter.
   Roughly an 8-10× difference.
```
:::

That ratio is why parameter-efficient methods exist, and why a 70B model that serves on one node needs a small cluster to fine-tune.

## LoRA

**LoRA** — low-rank adaptation — rests on one observation. Fine-tuning doesn't scatter arbitrary changes across a weight matrix; the adjustment it makes turns out to be describable by far fewer numbers than the matrix contains. So don't store the change as a full-size matrix. Store it as two thin ones whose product reconstructs it.

The saving is enormous: two 4096×16 matrices hold 131,000 numbers where the full change would need 16.8 million.

```diagram
   Frozen weight W  (d × d, e.g. 4096 × 4096 = 16.8M params)

   Instead of learning ΔW directly (16.8M params), learn:

       ΔW = B · A          where  A is r × d
                                  B is d × r
                                  r ≪ d  (typically 8-64)

   With r = 16:
     A: 16 × 4,096 =  65,536
     B: 4,096 × 16 =  65,536
                     ────────
                      131,072 params   vs  16.8M
                      → 0.8% of the full matrix

   Forward pass:  h = W·x + (B·A)·x · (α/r)
                      ────   ───────
                      frozen  trainable
```

:::derive Why LoRA collapses the memory bill
```
   7B model, LoRA rank 16 on attention projections:
     trainable parameters ≈ 20M  (0.3% of the model)

     frozen weights (can be quantized!)   7B × 2   =  14 GB
     LoRA weights                        20M × 2   = 0.04 GB
     LoRA gradients                      20M × 2   = 0.04 GB
     Adam states for LoRA only           20M × 8   = 0.16 GB
     activations                                    ~8 GB
                                                    ───────
     total                                        ≈ 22 GB

   → fits one 24 GB GPU, versus 2× 80 GB for full fine-tuning.

   QLoRA goes further: quantize the frozen base to NF4.
     base 7B × 0.5 bytes  =  3.5 GB
     total                ≈ 10 GB  → a consumer GPU
```
:::

**The serving property is the one that matters architecturally.** LoRA adapters are small — tens of megabytes — and can be applied to a shared base model at inference time.

```diagram
   MULTI-TENANT LoRA SERVING

     one base model in GPU memory  (14 GB)
        + adapter A (30 MB)   → customer A's tuned behaviour
        + adapter B (30 MB)   → customer B
        + ...
        + adapter Z (30 MB)   → customer Z

     Requests from different customers batch TOGETHER,
     each with its own adapter applied in the kernel.

   → 100 fine-tuned "models" in the memory of one,
     with near-full batching efficiency.
```

This is how fine-tuning-as-a-service is economically possible. Serving 100 separately fine-tuned 7B models would need 100 × 14 GB; serving 100 LoRA adapters over one base needs 14 GB + 3 GB. Systems like S-LoRA and Punica implement the batched multi-adapter kernels.

The alternative — **merging** the adapter into the base weights — gives zero inference overhead but produces a distinct full model, losing the multi-tenancy. Merge when you're serving one tuned model at volume; keep adapters separate when you're serving many.

| Hyperparameter | Typical | Effect |
|---|---|---|
| **Rank r** | 8–64 | Capacity. Higher for large behaviour changes, lower for style |
| **Alpha α** | Often 2r | Scales the update; the effective learning rate for the adapter |
| **Target modules** | Attention projections, sometimes FFN too | More modules = more capacity and memory |
| **Dropout** | 0.05–0.1 | Regularisation on small datasets |

## Preference optimization

**Supervised fine-tuning** — showing the model correct examples and having it imitate them — can only express "this is right". It has no way to say "both of these are plausible, but this one is better", which is exactly the judgement that separates a helpful assistant from a merely accurate one. Teaching that requires comparisons rather than answers.

```viz
{

  "caption": "The classical RLHF pipeline. DPO collapses the last two stages into one.",
  "steps": [
    { "label": "Pretrain", "sub": "next-token prediction on a large corpus", "accent": "#38bdf8" },
    { "label": "SFT", "sub": "imitate high-quality demonstrations", "accent": "#22d3ee" },
    { "label": "Reward model", "sub": "train a scorer on human A-vs-B preferences", "accent": "#a78bfa" },
    { "label": "RL (PPO)", "sub": "optimize the policy against the reward model", "accent": "#fb7185" }
  ]
}
```

**PPO's infrastructure cost is the thing to know:** it requires *four* models in memory simultaneously — the policy being trained, a frozen reference for the KL penalty, the reward model, and a value model. Plus a generation loop inside the training loop, since you must sample responses to score them. It is roughly 4–8× the cost of supervised fine-tuning and considerably harder to keep stable.

**DPO** (direct preference optimization) is the simplification that changed practice. The insight: the optimal policy under a reward model has a closed form, so you can reformulate preference learning as a *classification loss* directly on preference pairs — no reward model, no RL loop, no sampling during training.

```diagram
   PPO                              DPO

   4 models in memory               2 models (policy + reference)
   generate during training         no generation, offline pairs
   reward model to train first      no reward model
   unstable, needs careful tuning   stable, looks like ordinary SFT
   ~4-8× SFT cost                   ~2× SFT cost

   → DPO is what most teams should use.
     PPO retains an edge when you can generate fresh
     on-policy data, which is why frontier labs still use it.
```

Variants worth recognising: **IPO** (fixes a DPO overfitting failure mode), **KTO** (works from thumbs-up/down rather than pairs — much easier data to collect), and **GRPO** (group-relative, used for reasoning training, dispenses with the value model).

:::trap Catastrophic forgetting is the default outcome
Fine-tune on 5,000 customer-support examples and the model gets better at support and measurably worse at everything else — arithmetic, code, general reasoning. The weights moved, and nothing was holding the rest in place.

Mitigations, roughly in order of practicality:
- **Use LoRA with a small rank.** Constraining the update constrains the damage.
- **Mix in general data**, typically 10–30% of the training mixture.
- **Lower learning rate, fewer epochs.** Most fine-tunes need 1–3 epochs; more is usually harmful.
- **Evaluate on general benchmarks too**, not only your task. This is the step teams skip, and it's how a fine-tuned model ships with a quiet regression in an unrelated capability.
:::

## Data is the whole thing

The consistent finding across the literature: **a thousand carefully curated examples beat a hundred thousand mediocre ones.**

- **Quality over quantity.** LIMA got strong instruction-following from 1,000 examples. Noisy data actively teaches the wrong behaviour.
- **Diversity over volume.** Coverage of the input distribution matters more than count within any one mode.
- **Consistency.** If two examples handle the same situation differently, you're teaching the model to be inconsistent.
- **Format exactly as you'll serve.** Training and serving prompt templates must match precisely, down to whitespace and special tokens. Mismatch here is the single most common cause of "the fine-tune didn't work."
- **Held-out evaluation from the start.** Not a benchmark — your task, your distribution, scored the way you actually care about.

:::exercise Cost out the options
You classify support tickets into 40 categories. Currently: a frontier model with a 1,500-token prompt, 2M tickets/day, 94% accuracy.

1. Current daily cost at any current pricing? Latency per ticket?
2. Option A: fine-tune an 8B model on 50,000 labelled examples. Estimate training cost (LoRA, one GPU, a few hours) and serving cost at 2M/day. What accuracy would make this worth it?
3. Option B: prompt a small model with 20 few-shot examples. Cost, and what accuracy would you expect?
4. Where do the 50,000 labels come from? What's the cost of generating them with the frontier model, and how does that change the payback period?
5. Categories change quarterly. What does that do to the comparison — and which option handles it better?
:::

## What to carry forward

- **Fine-tuning teaches style and format, not facts.** Facts are a retrieval problem.
- **Training memory ≈ 16–20 bytes/parameter** versus ~2 for inference — an 8–10× gap.
- **LoRA trains ~0.3% of parameters** and, crucially, lets **many adapters share one base model in memory**.
- **DPO replaced PPO** for most teams: two models instead of four, no RL loop, comparable results.
- **Catastrophic forgetting is the default.** Mix general data, keep ranks low, evaluate broadly.
- **The strongest economic case is distillation** — big model generates the data, small model serves it.
